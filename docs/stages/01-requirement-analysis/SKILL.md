# Requirement Analysis Skill

## 目标

帮助人用最少的输入，完成一份清晰、可执行、可继续推进的阶段 1 需求分析文档。

这个 Skill 的核心是**交互式对话**，不是让用户填写模板，也不是让 AI 一次性写完整份文档。AI 应通过“用户说出想法 → AI 总结 → AI 提问 → 用户回答 → AI 更新理解”的方式，逐步把需求梳理清楚。

## 最终文档名称

阶段 1 定稿后，必须将最终需求分析文档保存为：

```text
code/docs/requirement-analysis.md
```

文件名和路径固定不变。阶段 2 必须直接读取 `requirement-analysis.md`。

文档的章节结构见本文件下面的「最终文档结构」一节。这是供 AI 生成文档使用的结构说明，不是要用户填写的模板。

## 最终文档结构

定稿文档使用下面的章节结构。这是 AI 的生成依据，不需要用户填写。

生成时必须遵守：

1. 只使用交互过程中用户确认过的信息；
2. 不清楚的内容标记为“待确认”，不凭空编造；
3. 每个未确定事项都必须在文档中体现出最终处理结果；
4. 文档语言简洁、可执行、可验证。

### 1. 项目概述

- 项目要做什么
- 核心方向
- 一句话说明产品定位

### 2. 目标用户

- 主要使用者是谁
- 使用场景
- 用户具备的前提条件

### 3. 要解决的问题

- 当前痛点
- 为什么值得解决

### 4. 需求目标

- 按核心目标逐条列出
- 每条目标说明用户能获得什么

### 5. 模块边界说明

- 以表格列出各模块及其职责
- 用说明条目写明模块之间的边界规则
- 明确容易重叠的内容归属哪个模块
- 记录合并、拆分或排除的模块及原因

### 6. 成功标准

- 用户在完成后能做到什么
- 判断需求完成的可验证标准

### 7. 范围与边界

- 必做：本次一定要完成的内容
- 暂不做：明确排除的内容

### 8. 约束与风险

- 主要限制：时间、技术、资源、规则等
- 主要风险：需求变动、技术难度、依赖问题等

### 9. 未确定事项处理结果

以表格记录每个未确定事项及其最终处理结果：

| 编号 | 未确定事项 | 影响范围 | 处理方式 | 最终结论 |
|---|---|---|---|---|
| U-01 |  |  | 确认 / 排除 / 延后 / 继续追问 |  |

### 10. 人工确认结论

- 用户已确认的内容
- 明确延期的事项及后续处理方式
- 阶段完成判断

## 适用场景

- 阶段 1：需求分析阶段
- 单人使用
- 用户只有一个想法或一句话描述
- 希望通过对话让 AI 帮助澄清和收敛需求

## 交互式工作流程

### 第 1 步：接收用户的想法

用户只需要用一句话说出想做什么。例如：

> 我是养猫的用户，我想做一个跟猫相关的 App，可以记录猫咪成长，还能提醒打疫苗和驱虫。

不要要求用户填写模板、回答一长串问题，或先提供完整信息。

### 第 2 步：总结当前理解

AI 先用简短的话复述目前理解到的内容，让用户确认方向是否正确。例如：

> 我理解你想做一个面向养猫用户的 App，主要包含成长记录和健康提醒两个方向，对吗？

### 第 3 步：提出少量关键问题

AI 每轮只提出少量最关键的问题，不要一次问太多。优先围绕最影响需求范围的点提问。

推荐的提问顺序：

1. 这个东西到底解决了谁的什么问题？
2. 目标用户是谁，使用场景是什么？
3. 做成什么样才算“成功”？
4. 哪些内容属于必做，哪些属于暂时不做？
5. 现在有哪些已知限制、风险或假设？
6. 还有哪些问题目前还不确定，需要后续再确认？

每轮提问后，等用户回答，再更新理解并继续追问下一组。

### 第 4 步：逐步整理成需求草稿

当关键信息基本收集完成后，AI 整理出一份需求草稿，结构为：

- 项目概述
- 目标用户
- 要解决的问题
- 需求目标
- 模块边界说明
- 成功标准
- 范围与边界
- 约束与风险
- 未确定事项

草稿不是最终定稿，而是给用户检查。

### 第 5 步：请用户确认与修正

AI 提醒用户检查：

- 需求是否足够清晰
- 成功标准是否可验证
- 范围是否合理
- 有没有遗漏的关键点
- 是否有明显的优先级差异

如果用户觉得不够清晰，AI 应继续协助改写，而不是直接结束。

### 第 6 步：AI 自查需求的完整性与一致性

在草稿得到用户初步确认后、处理未确定事项之前，AI 必须自己对文档做一次检查，主动找出**重叠、遗漏和矛盾**，而不是等用户指出。

AI 应至少检查以下几类问题：

1. **模块边界重叠**
   - 同一个内容是否出现在多个模块（例如“就医/用药”同时出现在“病例”和“生活记录”）
   - 两个模块是否实际是同一件事（例如“成长记录”和“生活记录”）
   - 需要合并、拆分或明确边界
2. **模块定义空泛**
   - 是否存在只有一句话、无法执行或无法判断边界的模块
3. **章节自相矛盾**
   - 例如写“汇总全部内容”，但实际只列出了部分内容
4. **概述与正文不一致**
   - 项目概述提到的范围是否与需求目标一致
5. **必备能力遗漏**
   - 编辑、删除、查看、关联到具体对象等基础能力是否缺失
   - 记录、条目等业务对象是否明确关联到对应的主体对象
6. **风险与需求不对应**
   - 只写在“风险”里、但应该明确成需求的内容
7. **术语与命名**
   - 是否存在含义模糊、容易混淆或容易重复的名称

AI 应把发现的问题列出来，并区分：

- **必须澄清**：影响结构或导致无法执行
- **建议补充**：影响完整性

然后逐条向用户提出，用户确认后更新文档。

> 如果自查或后续对话引出了新的待确认点，必须一并加入未确定事项列表并继续处理，直到列表清空。

### 第 7 步：逐项处理未确定事项

需求草稿中只要存在未确定事项，AI 就不能直接定稿。AI 应把这些事项逐项列出，并询问用户如何处理。

每个未确定事项至少提供以下处理选项：

1. 现在确认一个明确结论；
2. 暂时排除，不纳入当前版本；
3. 保留为后续待办，并说明何时或进入哪个阶段再确认；
4. 继续追问，直到问题足够清晰。

AI 应使用类似下面的格式进行确认：

| 编号 | 未确定事项 | 影响范围 | 处理方式 | 最终结论 |
|---|---|---|---|---|
| U-01 |  |  | 确认 / 排除 / 延后 / 继续追问 |  |

只有当用户明确处理了每个未确定事项，或者明确同意将其作为已记录的后续待办时，才可以进入最终定稿。

### 第 8 步：最终定稿

在满足以下条件时，才可以形成最终版本：

- 目标用户明确
- 问题清晰
- 需求目标明确
- 成功标准可验证
- 范围和边界清楚
- 主要限制和风险已说明
- 每个未确定事项都已确认、排除或明确延期
- 需求文档中保留了延期事项及其后续处理方式

最终输出应保存为 `code/docs/requirement-analysis.md`，作为阶段 2 直接读取的需求分析文档。

## AI 的提问策略

AI 应始终以“引导式对话”方式与用户交流，而不是一上来就直接生成文档，也不要一次抛出大量问题。

推荐的对话节奏：

1. 先总结当前已知信息
2. 再指出哪些信息还不够清晰
3. 只提出少量最关键问题
4. 等用户回答后，更新理解
5. 重复提问和更新，直到信息足够
6. 再整理成草稿
7. 最后请用户确认并处理未确定事项

提问时应使用日常语言，避免一次列出十几条问题，避免让用户感觉像在填表。

## 可直接复制的提示词

### 版本 A：从一句话想法开始

```text
我现在开始做阶段 1：需求分析阶段。

我的想法是：
[用一句话描述你的想法]

请你按下面的方式帮我推进：
1. 先总结你目前理解到的内容，让我确认方向；
2. 每轮只问我少量最关键的问题；
3. 等我回答后，更新你的理解并继续追问；
4. 信息足够后，帮我整理成需求分析草稿；
5. 让我确认草稿是否准确；
6. 再逐项询问我未确定事项如何处理；
7. 最后生成 requirement-analysis.md。
```

### 版本 B：让 AI 主动引导

```text
我想做阶段 1 的需求分析。

我目前只有一个大概的想法，还没有想清楚细节。
请你通过提问的方式引导我把需求说清楚。

要求：
1. 不要让我填写模板；
2. 一次只问最关键的几个问题；
3. 根据我的回答继续追问；
4. 最后帮我整理成需求分析文档。
```

### 版本 C：只有模糊方向

```text
我有个模糊的想法：[描述你的想法]
我还没想清楚要做成什么样。

请你先告诉我为了把需求理清楚，最需要先确认哪几个问题，然后一个问题一个问题地问我，最后帮我生成需求分析文档。
```

## 一致性自查清单

在定稿前，AI 必须逐项检查：

- [ ] 模块之间是否有内容重叠
- [ ] 是否有两个模块实际是同一件事
- [ ] 是否有模块定义空泛、无法执行
- [ ] 是否已写出模块边界说明，并交代容易重叠内容的归属
- [ ] 章节之间是否有自相矛盾
- [ ] 项目概述与需求目标是否一致
- [ ] 是否缺少编辑、删除、关联等基础能力
- [ ] 记录、条目等业务对象是否明确关联到对应的主体对象
- [ ] 写在“风险”里的内容是否需要提升为需求
- [ ] 命名是否清晰、无歧义
- [ ] 新发现的待确认点是否已加入列表并处理

## 检查清单

在最终定稿前，建议确认这些问题：

- 目标用户是否明确？
- 问题是否具体且真实？
- 需求是否清楚、可执行？
- 成功标准是否可验证？
- 范围是否清楚？
- 主要约束和风险是否已记录？
- 未确定事项是否已经逐项处理？

## 不要做的事

- 不要让用户预先填写模板
- 不要一次性抛出大量问题
- 不要一开始就写技术方案
- 不要在信息不足时强行补全细节
- 不要让需求分析文档写得像设计文档
- 不要跳过“用户确认”这一步
- 不要在未经自查的情况下直接定稿
- 不要把模块重叠、定义空泛或章节矛盾留给用户发现

## 最终交付物

最终交付物应为：

- `code/docs/requirement-analysis.md`
- 每个未确定事项及其最终处理结果

## 目标语气

AI 在这个阶段的语气应该是：

- 鼓励用户说出想法
- 一次只问少量关键问题
- 引导用户补齐关键点
- 在用户还没想清楚时，不直接落定复杂内容
- 最终帮助用户形成可继续推进的需求说明
