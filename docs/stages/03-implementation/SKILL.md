# Implementation Skill（阶段 3A + 3B）

## 目标

本 Skill 负责阶段 3 的两步，严格有先后关系。

阶段 3A：技术架构选型

```text
读取 requirement-analysis.md
→ AI 总结需求中的形态、规模和约束
→ AI 分轮询问运行形态、技术偏好、部署环境、数据规模和维护方式
→ AI 给出 2~3 个候选架构方案及取舍对比
→ 用户选定方案并记录为架构决策
→ 建立技术栈、分层、模块划分、数据与接口约定
→ AI 自查架构与需求的一致性
→ 用户逐项确认
→ 生成 tech-architecture.md
```

阶段 3B：任务拆解与代码实现

```text
读取已确认的 tech-architecture.md
→ 确认实现顺序与最小可运行闭环
→ 逐模块拆解可独立执行的任务
→ 确认依赖关系与并行分组
→ 生成 tasks.md
→ 生成 api-design.md
→ 执行实现并更新任务状态
→ 用户确认
→ 定稿任务文档与 API 文档
```

技术架构选型是研发阶段的前置步骤。没有确认的 `tech-architecture.md`，不允许开始拆解任务和编写业务代码。

阶段 3B 必须在阶段 3A 完成且用户确认 `tech-architecture.md` 之后才能开始。

## 固定文件

阶段 1 输入：

```text
code/docs/requirement-analysis.md
```

阶段 2 参考输入（可选）：

```text
code/docs/ux-design.md
code/docs/ui-design.md
```

阶段 3A 输出：

```text
code/docs/tech-architecture.md
```

阶段 3B 输出：

```text
code/docs/tasks.md
code/docs/api-design.md
```

编码子 Skill（任务数量较多时使用）：

```text
docs/stages/03-implementation/coding/SKILL.md
docs/stages/03-implementation/coding/templates/agent-task-brief.md
```

文件名固定，不得改名，否则后续阶段无法读取。

如果 `requirement-analysis.md` 不存在，或阶段 1 仍有未处理的未确定事项，不能开始本 Skill。

# 阶段 3A：技术架构选型

## 3A 的职责

3A 只处理：

- 交付形态与运行环境
- 架构风格与系统分层
- 技术栈选型（语言、框架、存储、工具链）
- 需求模块到代码模块的映射
- 数据结构与存储设计
- 接口风格与鉴权约定
- 工程结构与配置管理
- 非功能性要求（性能、可靠性、安全、成本）
- 构建、运行与部署方式
- 选型理由与被放弃的备选方案

3A 不处理：

- 新增或修改需求
- 修改已确认的用户流程、页面职责和交互逻辑
- 视觉样式细节
- 单个任务的拆解（属于 3B）
- 具体业务代码实现（属于 3B）

> 架构选型的目标是“够用且可维护”，不是“先进且完备”。单人长期维护的项目，简单优先于灵活。

## 3A 交互式工作流程

### 第 1 步：读取需求并总结架构约束

AI 必须先读取：

```text
code/docs/requirement-analysis.md
```

提取并总结与架构有关的内容：

- 产品定位和交付形态的线索
- 目标用户和使用场景
- 需求目标
- 模块边界说明
- 成功标准
- 约束与风险
- 已处理的未确定事项

不要要求用户重新填写项目名称、产品背景或技术信息。

读完需求后，AI 先用简短内容说明：

- 当前理解的交付形态
- 需求涉及的模块数量和规模
- 已经明确的限制（成本、环境、数据、合规）
- 目前还不清楚、会直接影响选型的架构问题

等待用户确认方向后再继续提问。

### 第 2 步：分轮询问架构问题

AI 每轮只问少量最关键的问题，不要一次性生成完整架构方案，也不要一次抛出大量问题。

推荐询问顺序：

1. 这个东西以什么形态交付，由谁来运行它？
2. 有没有已经确定必须使用、或者你更熟悉的技术？
3. 部署在哪里，有没有成本、网络或内网限制？
4. 数据量、并发量、离线使用或隐私有没有硬要求？
5. 只给一个人用，还是需要多人或多端共同使用？
6. 你打算怎么长期维护它，能投入多少精力？

用户回答后，AI 必须：

1. 更新当前理解；
2. 指出仍然不清楚的点；
3. 再提出下一组少量问题。

### 第 3 步：提出候选方案并对比

信息基本收集完成后，AI 必须先给出 2~3 个候选架构方案，而不是直接锁定一套技术栈。

对比至少包含：

| 方案 | 架构风格 | 技术栈概要 | 适合场景 | 主要代价 |
|---|---|---|---|---|
| 方案 A |  |  |  |  |
| 方案 B |  |  |  |  |

要求：

- 每个方案都要说明它牺牲了什么，不能只列优点；
- 方案必须来自需求中的真实约束，不得凭个人偏好推荐；
- 必须给出 AI 的推荐方案和推荐理由，但由用户拍板；
- 用户选定后，把选择和放弃理由记录为架构决策（`ADR-###`）。

### 第 4 步：确认选型并建立架构设计

用户选定方案后，AI 逐项确认并记录：

- 技术栈：语言、运行时、核心框架、存储、工具链；
- 系统分层和每一层的职责；
- 需求模块到代码模块的映射；
- 数据实体和存储方式；
- 接口风格、鉴权和错误约定；
- 工程目录结构和配置管理方式；
- 构建、本地运行和部署方式。

技术栈中的每一项都必须写明确切的版本要求，避免以后无法复现。

### 第 5 步：自查架构完整性和一致性

用户初步确认后，AI 必须主动检查，不要等用户发现问题。

至少检查：

1. 需求中的每个模块是否都有对应的代码模块；
2. 是否引入了需求之外的功能、模块或中间件；
3. 是否与已确认的 UX/UI 文档矛盾；
4. 是否为了“以后可能要用”引入了不必要的复杂度；
5. 每个选型是否都有理由，并说明了被放弃的备选方案；
6. 版本约束是否明确、可复现；
7. 分层与模块职责是否重叠、是否存在空泛模块；
8. 数据实体是否覆盖需求中需要保存的信息；
9. 接口约定是否覆盖 UX 中需要的数据交互；
10. 安全、隐私、成本和合规等硬约束是否被忽略；
11. 本地运行和部署方式是否真的可执行；
12. 命名和编号是否清晰、前后一致。

AI 必须将发现的问题分为：

- **必须澄清**：会影响架构可行性或模块划分；
- **建议补充**：不影响可行性，但影响完整性。

然后逐条向用户询问并更新方案。

### 第 6 步：处理架构待确认事项

所有 `ARCH-TBD-###` 必须逐项询问用户，处理方式为：

- 确认
- 排除
- 延后
- 继续追问

如果处理某一事项时产生新的待确认点，必须加入列表并继续处理，直到没有未处理事项。

### 第 7 步：用户确认后生成文档

AI 应向用户展示最终架构草稿，并明确询问：

- 交付形态和运行方式是否准确；
- 选型是否符合自己的技术栈和维护能力；
- 模块划分是否与需求一致；
- 数据、接口和部署约定是否清楚；
- 自查发现的问题是否已经处理；
- 是否确认生成最终技术架构文档。

用户未确认时，不得保存最终文件。

用户确认后，生成：

```text
code/docs/tech-architecture.md
```

这个文件是阶段 3B 拆解任务的唯一架构输入。

## 技术架构文档结构

最终 `tech-architecture.md` 至少包含：

1. 架构目标与约束（含非功能性约束）
2. 交付形态与运行环境
3. 技术栈与分层
4. 模块划分与需求模块映射
5. 数据与存储
6. 接口约定
7. 构建、运行与部署
8. 架构决策记录
9. 技术风险
10. 待确认事项处理结果
11. 人工确认结论

不要为了凑章节把内容拆得太细。判断标准是「这一节会不会被后续阶段真正查阅」，不会被查阅的应当合并或删除。

其中：

- 「架构目标与约束」必须逐条对应需求文档中的目标、成功标准和约束，不能凭空产生；
- 「模块划分与需求模块映射」必须覆盖需求文档「模块边界说明」中的全部模块；
- 「技术栈与分层」中的每一项都要写明具体版本；
- 「架构决策记录」使用下面的表格：

| 编号 | 决策点 | 背景 | 最终选择 | 被放弃的方案 | 放弃原因 |
|---|---|---|---|---|---|
| ADR-001 |  |  |  |  |  |

生成时必须遵守：

1. 只使用交互过程中用户确认过的信息；
2. 不清楚的内容标记为“待确认”，不凭空编造；
3. 每个待确认事项都必须体现出最终处理结果；
4. 不写无法执行、无法验证的空泛架构描述。

## 3A 编号规则

| 对象 | 编号格式 | 示例 |
|---|---|---|
| 架构决策 | `ADR-###` | `ADR-001` |
| 代码模块 | `MODULE-###` | `MODULE-001` |
| 待确认事项 | `ARCH-TBD-###` | `ARCH-TBD-001` |

只给真正需要被后续引用的对象编号，其余内容直接用名称表述。`MODULE-###` 必须在任务文档中保持一致。需求文档中的模块名称必须原样复用，不得在架构阶段重新命名。

## 可直接复制的启动提示词

```text
我现在开始阶段 3A：技术架构选型。

请先读取：
code/docs/requirement-analysis.md

我不填写架构模板，请通过交互式对话引导我完成：
1. 先总结需求中的交付形态、模块和已知约束；
2. 每轮只问少量最关键的架构问题；
3. 先给出 2~3 个候选方案和取舍对比，并说明你的推荐和理由；
4. 我选定方案后，再一起确定技术栈、分层、模块映射、数据、接口和部署方式；
5. 主动检查架构与需求是否一致、是否过度设计、选型是否有理由；
6. 将自查发现的问题逐条向我确认；
7. 逐项处理所有待确认事项，包括过程中新增的事项；
8. 我最终确认后，生成：
code/docs/tech-architecture.md

不要新增需求之外的功能，不要修改已确认的 UX/UI 流程，不要开始拆任务或写业务代码。
```

## 完成条件

- [ ] 已读取 `requirement-analysis.md`
- [ ] 已确认交付形态、运行环境和维护方式
- [ ] 已给出 2~3 个候选方案及取舍对比
- [ ] 用户已选定方案，并记录为架构决策
- [ ] 技术栈每一项都有理由和版本要求
- [ ] 需求模块已全部映射到代码模块
- [ ] 数据结构、接口和部署方式已明确
- [ ] 已完成架构与需求的一致性自查
- [ ] 自查问题已逐项处理
- [ ] 所有 `ARCH-TBD-###` 已处理
- [ ] 用户已确认最终架构草稿
- [ ] 已生成 `tech-architecture.md`

## 不要做的事

- 不要要求用户填写架构模板
- 不要跳过读取阶段 1 需求
- 不要一次性抛出大量问题
- 不要只给一个方案就让用户接受
- 不要只列优点、不写代价和放弃理由
- 不要为了“以后可能要用”引入中间件或抽象层
- 不要新增需求之外的功能或模块
- 不要修改已确认的 UX/UI 流程、页面职责和交互逻辑
- 不要在架构未确认时开始拆任务或写代码
- 不要在用户确认前生成最终 `tech-architecture.md`

# 阶段 3B：任务拆解与代码实现

## 3B 的职责

3B 只处理：

- 实现顺序与最小可运行闭环
- 任务拆解、依赖关系与并行分组
- 每个任务的验收标准
- 任务状态跟踪
- API 文档
- 数据结构实现
- 代码实现
- 文档与实现的一致性

3B 不处理：

- 重新做技术架构选型
- 新增或修改需求
- 修改用户流程、页面职责和交互逻辑
- 视觉样式设计

> 发现架构不可行时，必须回到阶段 3A 修改 `tech-architecture.md`，不要在代码里绕过去。

## 3B 交互式工作流程

### 第 1 步：读取技术架构文档

AI 必须先读取：

```text
code/docs/tech-architecture.md
```

提取并总结：

- 选定的架构风格和技术栈
- 系统分层和代码模块清单
- 数据实体
- 接口约定
- 构建和运行方式
- 已识别的技术风险

如果 `tech-architecture.md` 不存在，或仍有未处理的 `ARCH-TBD-###`，不能开始 3B。

### 第 2 步：确认实现顺序和最小可运行闭环

AI 应与用户确认：

- 先做哪个模块，后做哪个模块；
- 哪个组合构成“能跑起来的最小闭环”；
- 哪些部分现在不做。

AI 应给出建议顺序和理由，但由用户确认。默认原则是先打通最小闭环，再扩展功能。

### 第 3 步：逐模块拆解任务并确认依赖

AI 按架构文档中的 `MODULE-###` 逐模块拆解任务，每个任务必须满足：

- 可独立执行，不依赖未完成的隐式前提；
- 有明确的输入和产出文件；
- 有可验证的验收标准；
- 写明依赖的其他任务。

任务粒度以“一次能做完并验证”为准，不要把整个模块写成一个任务，也不要拆成没有意义的一行改动。

拆解完成后，AI 应明确：

- 每个任务的依赖项；
- 哪些任务可以并行执行；
- 哪些任务位于关键路径，延期会影响整体进度。

并行分组用于支持 AI 并发开发与任务进度跟踪。

### 第 4 步：生成任务文档和 API 文档

生成：

```text
code/docs/tasks.md
```

```text
code/docs/api-design.md
```

API 文档必须与架构文档中的接口约定一致，不得新增未确认的接口或字段。

### 第 5 步：执行实现并更新任务状态

实现过程中，AI 必须：

- 按已确认的任务顺序推进，不擅自扩大范围；
- 每完成一个任务，更新任务状态和实际产出；
- 发现架构不可行时，停下来回到 3A 修改架构文档；
- 发现需求或 UX 问题时，回到对应阶段修改，不要在实现里静默改掉。

任务数量较多时，应改用并行编码方式：按 [coding/SKILL.md](coding/SKILL.md) 先冻结契约，再按模块切分给多个 AI 子代理并行实现，最后由协调者统一完成集成与端到端验证。任务书模板见 [coding/templates/agent-task-brief.md](coding/templates/agent-task-brief.md)。

### 第 6 步：处理实现阶段的待确认事项

所有 `TASK-TBD-###` 必须逐项询问用户，处理方式为：

- 确认
- 排除
- 延后
- 继续追问

过程中产生的新事项同样加入列表，直到没有未处理事项。

### 第 7 步：定稿

用户确认后，任务文档和 API 文档定稿，作为阶段 4 测试阶段的输入。

## 任务文档结构

`tasks.md` 至少包含：

1. 实现范围与顺序说明（含最小可运行闭环）
2. 任务清单
3. 任务依赖与并行分组
4. 任务进度状态汇总
5. 待确认事项处理结果
6. 人工确认结论

任务清单使用下面的表格：

| 任务编号 | 任务名称 | 模块 | 依赖项 | 验收标准 | 状态 |
|---|---|---|---|---|---|
| TASK-001 |  | MODULE-001 | 无 |  | 待处理 |

- 「模块」列填 `MODULE-###`，不属于单一模块的基础设施任务填「公共」。
- 任务粒度按项目规模定，小型项目十个左右任务是正常的，不必强行凑数或压缩。
- 已确认不做的任务直接从表中删除，排除范围由需求文档记录，不要留废弃行。

任务状态只能取以下值：

| 状态 | 含义 |
|---|---|
| 待处理 | 尚未开始 |
| 进行中 | 正在实现 |
| 待验证 | 已实现，等待验证 |
| 已完成 | 已通过验收标准 |
| 已阻塞 | 因依赖或问题无法继续 |

状态为「已阻塞」时，在任务表下方用一小段说明原因和解除条件，不要为偶尔出现的阻塞在表里长期加一列。

## API 文档结构

`api-design.md` 至少包含：

1. 接口约定
2. 接口清单
3. 数据结构
4. 错误与异常约定
5. 待确认事项处理结果

接口不限于 HTTP。有远端服务时记录协议、路径、鉴权和错误码；本地应用或桌面应用记录服务层和仓储层的方法；确实没有接口时，直接写明「本项目无外部接口」并说明原因，不要为凑格式编造接口。

接口清单使用下面的表格，「形态」列按项目实际情况填写（HTTP / 本地方法 / CLI 等）：

| 接口编号 | 名称 | 形态 | 对应模块 | 用途 | 状态 |
|---|---|---|---|---|---|
| API-001 |  | 本地方法 | MODULE-001 |  | 待处理 |

## 3B 编号规则

| 对象 | 编号格式 | 示例 |
|---|---|---|
| 任务 | `TASK-###` | `TASK-001` |
| 接口 | `API-###` | `API-001` |
| 待确认事项 | `TASK-TBD-###` | `TASK-TBD-001` |

任务文档必须复用架构文档中的 `MODULE-###` 编号，不得重新编号。3B 只保留一个待确认清单，编号为 `TASK-TBD-###`，新发现的条目加入其中，不要另开一套编号。

## 可直接复制的启动提示词

```text
我现在开始阶段 3B：任务拆解与代码实现。

请先读取：
code/docs/tech-architecture.md

我不填写任务模板，请通过交互式对话引导我完成：
1. 先总结架构中的分层、模块、数据和接口约定；
2. 和我确认实现顺序和最小可运行闭环；
3. 逐模块拆出可独立执行、有验收标准的任务；
4. 明确任务依赖和可并行分组；
5. 生成任务文档；
6. 生成 API 文档；
7. 实现过程中持续更新任务状态；
8. 逐项处理所有待确认事项；
9. 我最终确认后，定稿：
code/docs/tasks.md
code/docs/api-design.md

不要重新做技术选型，不要修改需求和已确认的 UX/UI 流程。如果发现架构不可行，先告诉我并回到阶段 3A。
```

## 完成条件

- [ ] 已读取 `tech-architecture.md`
- [ ] `tech-architecture.md` 无未处理的 `ARCH-TBD-###`
- [ ] 已确认实现顺序和最小可运行闭环
- [ ] 架构中的每个 `MODULE-###` 都有对应任务
- [ ] 每个任务都有依赖项、执行方式和验收标准
- [ ] 已标注可并行分组和关键路径
- [ ] 已生成 `tasks.md`
- [ ] 已生成 `api-design.md`
- [ ] 任务状态可持续更新
- [ ] 所有 `TASK-TBD-###` 已处理
- [ ] 实现未改动需求、UX/UI 和已确认的架构
- [ ] 用户已确认最终任务文档和 API 文档

## 不要做的事

- 不要要求用户填写任务模板
- 不要跳过读取 `tech-architecture.md`
- 不要在架构未确认时开始拆任务
- 不要在实现阶段重新选型
- 不要新增需求之外的功能或接口
- 不要修改已确认的 UX/UI 流程和页面职责
- 不要留下没有验收标准的任务
- 不要把阻塞中的任务继续当作进行中
- 不要把待确认事项留给用户自己发现
- 不要在用户确认前定稿任务文档和 API 文档

## 约束

研发阶段不能修改已确认的需求、UX 和 UI。发现需求问题时回到阶段 1，发现交互问题时回到阶段 2A，发现视觉问题时回到阶段 2B，发现架构问题时回到阶段 3A。
