# 阶段 3：研发阶段

## 阶段目标

阶段 3 分为两个严格有先后关系的步骤：

```text
阶段 3A：技术架构选型
读取阶段 1 需求分析文档
→ AI 通过 Skill 与用户交互式询问
→ 对比 2~3 个候选架构方案并选定
→ 确定技术栈、分层、模块映射、数据与接口约定
→ 用户确认
→ 生成 tech-architecture.md

阶段 3B：任务拆解与代码实现
读取已确认的 tech-architecture.md
→ 确认实现顺序和最小可运行闭环
→ 逐模块拆解任务并明确依赖
→ 生成 tasks.md 和 api-design.md
→ 执行实现并更新任务状态
→ 定稿任务文档与 API 文档
```

技术架构选型是研发阶段的前置步骤。没有确认的 `tech-architecture.md`，不允许开始拆解任务和编写业务代码。

两个步骤严格有先后关系，阶段 3B 必须在 `tech-architecture.md` 确认后才能开始。

## 固定文件

阶段 1 输入：

```text
code/docs/requirement-analysis.md
```

阶段 2 参考输入（可选）：

```text
code/docs/ux-design.md
code/docs/ui-design.md
```

阶段 3 Skill：

```text
docs/stages/03-implementation/SKILL.md
```

阶段 3B 编码子 Skill（任务数量较多时使用）：

```text
docs/stages/03-implementation/coding/SKILL.md
docs/stages/03-implementation/coding/templates/agent-task-brief.md
```

阶段 3A 输出：

```text
code/docs/tech-architecture.md
```

阶段 3B 输出：

```text
code/docs/tasks.md
code/docs/implementation-record.md
code/docs/api-design.md
```

当前不需要用户填写任何模板。上述文档中，`tech-architecture.md`、`tasks.md` 与 `api-design.md` 由 AI 按 Skill 通过交互式问答生成；`implementation-record.md` 在实现过程中随进展记录。

阶段 3B 输出的代码位于仓库的 `code/` 目录：

code/backend    Python 3.12 + FastAPI 后端（uv 管理依赖）
code/frontend   React 19 + TypeScript + Vite 前端（构建产物交后端托管）
code/deploy     部署配置与运行手册
code/scripts    端到端验证脚本
```

如果 `requirement-analysis.md` 不存在，或阶段 1 仍有未处理的未确定事项，应先回到阶段 1。

# 阶段 3A：技术架构选型

## 目标

先回答“用什么做、怎么划分、怎么跑起来”，再进入任务拆解和编码。技术架构文档是阶段 3B 的唯一架构输入。

架构阶段关注：

- 交付形态与运行环境
- 架构风格与系统分层
- 技术栈选型与版本约束
- 需求模块到代码模块的映射
- 数据结构与存储设计
- 接口风格与鉴权约定
- 工程结构与配置管理
- 非功能性要求（性能、可靠性、安全、成本）
- 构建、运行与部署方式
- 选型理由与被放弃的备选方案

架构阶段不关注：

- 业务代码实现
- 单个任务的拆解
- 视觉样式细节
- 需求本身的增删改
- 已确认的用户流程和交互逻辑

## 架构交互流程

### 第 1 步：读取阶段 1 文档

AI 先读取 `requirement-analysis.md`，总结交付形态线索、模块边界、成功标准和约束，不要求你重新填写项目背景。

### 第 2 步：分轮询问架构问题

AI 每轮只问少量关键问题，通常围绕：

1. 以什么形态交付，由谁来运行？
2. 有没有必须使用、或者你更熟悉的技术？
3. 部署在哪里，有没有成本、网络或内网限制？
4. 数据量、并发、离线使用或隐私有没有硬要求？
5. 只给一个人用，还是需要多人或多端共同使用？
6. 你打算怎么长期维护它？

### 第 3 步：给出候选方案并选定

AI 必须先给出 2~3 个候选方案，说明每个方案适合的场景和需要付出的代价，再给出推荐和理由，由你拍板。选定结果记录为架构决策（`ADR-###`）。

### 第 4 步：建立架构设计

选定方案后，逐项确定技术栈、系统分层、模块映射、数据实体、接口约定、工程结构和部署方式。技术栈必须写明确切的版本要求。

### 第 5 步：自查并逐项确认

AI 主动检查架构与需求是否一致、是否过度设计、每个选型是否有理由、需求模块是否全部覆盖，把发现的问题分为“必须澄清”和“建议补充”后逐条和你确认。

### 第 6 步：处理待确认事项并生成文档

所有 `ARCH-TBD-###` 逐项处理为确认、排除、延后或继续追问。你最终确认后生成：

```text
code/docs/tech-architecture.md
```

## 技术架构文档结构

最终文档至少包含：

1. 架构目标与约束（含非功能性约束）
2. 交付形态与运行环境
3. 技术栈与分层
4. 模块划分与需求模块映射
5. 数据与存储
6. 接口约定
7. 构建、运行与部署
8. 架构决策记录
9. 技术风险
10. 待确认事项处理结果
11. 人工确认结论

## 编号规则

| 对象 | 编号格式 | 示例 |
|---|---|---|
| 架构决策 | `ADR-###` | `ADR-001` |
| 代码模块 | `MODULE-###` | `MODULE-001` |
| 待确认事项 | `ARCH-TBD-###` | `ARCH-TBD-001` |

只给真正需要被后续引用的对象编号。需求文档中的模块名称必须原样复用，不得在架构阶段重新命名。

# 阶段 3B：任务拆解与代码实现

## 目标

把已确认的架构拆成可独立执行、可验证、可跟踪的任务，同步产出 API 文档，并推进代码实现。

实现阶段关注：

- 实现顺序与最小可运行闭环
- 任务拆解、依赖关系与并行分组
- 每个任务的验收标准
- 任务状态跟踪
- API 文档
- 代码实现与文档的一致性

实现阶段不关注：

- 重新做技术选型
- 需求变更
- 用户流程和交互逻辑变更
- 视觉样式设计

## 实现交互流程

### 第 1 步：读取技术架构文档

AI 读取 `tech-architecture.md`，总结分层、模块清单、数据实体、接口约定和构建运行方式。如果仍有未处理的 `ARCH-TBD-###`，不能开始 3B。

### 第 2 步：确认实现顺序

和你确认先做哪个模块、哪个组合构成“能跑起来的最小闭环”、哪些现在不做。默认先打通最小闭环，再扩展功能。

### 第 3 步：逐模块拆解任务

按 `MODULE-###` 逐模块拆任务，每个任务必须可独立执行、有明确的输入和产出、有可验证的验收标准、写明依赖项。

### 第 4 步：确认依赖与并行分组

标出每个任务的依赖项、可以并行执行的任务，以及位于关键路径上的任务。

### 第 5 步：生成任务文档和 API 文档

生成：

```text
code/docs/tasks.md
code/docs/api-design.md
```

### 第 6 步：执行实现并更新状态

按确认的顺序推进，每完成一个任务就更新状态。发现架构不可行时回到阶段 3A，发现需求或交互问题时回到对应阶段。

## 任务文档结构

`tasks.md` 至少包含：实现范围与顺序说明、任务清单、任务依赖与并行分组、任务进度状态汇总、待确认事项处理结果、人工确认结论。

任务清单示例：

| 任务编号 | 任务名称 | 模块 | 依赖项 | 验收标准 | 状态 |
|---|---|---|---|---|---|
| TASK-001 |  | MODULE-001 | 无 |  | 待处理 |

「模块」列填 `MODULE-###`，公共基础设施任务填「公共」。任务状态只能取以下值：待处理 / 进行中 / 待验证 / 已完成 / 已阻塞。标记为「已阻塞」时，在表下方说明原因和解除条件。

## API 文档结构

`api-design.md` 至少包含：接口约定、接口清单、数据结构、错误与异常约定、待确认事项处理结果。

接口不限于 HTTP。有远端服务时记录协议、路径、鉴权和错误码；本地应用记录服务层和仓储层的方法；确实没有接口时直接写明「本项目无外部接口」并说明原因。

## 编号规则

| 对象 | 编号格式 | 示例 |
|---|---|---|
| 任务 | `TASK-###` | `TASK-001` |
| 接口 | `API-###` | `API-001` |
| 待确认事项 | `TASK-TBD-###` | `TASK-TBD-001` |

任务文档必须复用架构文档中的 `MODULE-###` 编号，不得重新编号。3B 只保留一个待确认清单，编号为 `TASK-TBD-###`。

## 约束

研发阶段不能修改已确认的需求、UX 和 UI：

- 发现需求问题 → 回到阶段 1
- 发现交互问题 → 回到阶段 2A
- 发现视觉问题 → 回到阶段 2B
- 发现架构问题 → 回到阶段 3A

## 下一步

阶段 3 完成后，进入：

- 阶段 4：测试阶段

阶段 4 会读取 `tasks.md` 和 `api-design.md` 作为测试输入。阶段 3B 的实际执行方式见 [implementation-record.md](../../../code/docs/implementation-record.md)；当任务数量较多时可按 [coding/SKILL.md](coding/SKILL.md) 组织编码。
