# Coding Skill（阶段 3B 编码）

## 目标

把 `tasks.md` 里的任务清单，通过「协调者 + 多个并行子代理」的方式落地为可运行的代码，并且保证：

- 多个子代理同时写代码时不互相覆盖、不重复实现、不违反已确认的架构；
- 契约（实体、接口、组件 props）只有一处定义，不会被各代理各自发明一套；
- 集成阶段的缺陷能被真实运行验证捕获，而不是靠「编译通过」交差。

## 何时使用

- `tasks.md` 已定稿，任务数量较多（经验值 10 个以上）；
- 任务之间已有清晰的依赖与并行分组；
- 场景是单体应用、前后端分离或多模块仓库（并行收益最大）；
- 反例：任务少、强耦合、或需要频繁改动同一批文件时，不并行更稳妥。

## 核心原则

### 1. 先冻结契约，再并行

这是整套流程的关键。并行的前提是「大家共用同一套定义」，因此协调者必须先自己完成契约层，且契约层要一次性写全：

```text
协调者先写（冻结）：
  数据库 schema
  实体（Entity）
  请求/响应对象（DTO / VO）
  枚举与常量
  Mapper 接口 + 全部 Service 接口
  公共层（统一响应体、错误码、异常处理、工具类）
  Mapper 接口对应的 XML statement id 清单

子代理后写（并行）：
  各模块的 ServiceImpl
  各模块的 Controller
  各模块的 Mapper XML 实现
```

契约层不冻结就开始并行，等于让每个代理自己发明枚举名和字段名，集成时必然大面积返工。

### 2. 写入范围互斥

每个子代理的指令里必须给出**明确的写入白名单**，并显式列出禁止修改的路径：

```text
只允许创建/修改：
  <模块A目录>/**
  src/main/resources/mapper/<模块A>*.xml

严禁修改：
  common/**、<其他模块>/**、pom.xml、application.yml、schema.sql、<入口类>.java
```

规则：

- 一个模块只交给一个代理，模块边界即写入边界；
- 共享文件（构建配置、入口类、全局样式、路由表、schema）一律由协调者持有；
- 子代理发现契约有问题时，**只能上报，不能改**，由协调者统一裁决后再改。

### 3. 前端并行要冻结「组件契约」

组件化项目里，父子组件可以并行开发，但必须先把 props / emits 冻结成文字契约，写进双方的任务书：

```text
TaskCard.vue
  props：task（Object，必填）、highlighted（Boolean，默认 false）
  emits：open（点击时抛出 task）
```

只冻结文件归属、不冻结组件契约，父子两边对不上号，集成时就是连锁修改。

### 4. 同步给子代理的上下文

每个子代理的任务书至少包含：

- 必读的阶段产物（需求 / UX / UI / 架构 / API / 任务文档）及其具体章节；
- 已冻结契约的清单（谁的签名、谁的职责）；
- 本次负责的 `TASK-###` 与其**验收标准原文**；
- 写入白名单与禁止修改清单；
- 可复用的既有资产（设计系统 CSS、工具函数、既有实现模式）；
- 范围外的负面清单（明确「不要做什么」），防止代理自由发挥。

### 5. 协调者自己做集成与验证

子代理只对「自己的文件能编译」负责；跨模块拼装、真实运行、端到端验证必须由协调者承担。
**编译通过不等于能跑**，集成阶段才是真缺陷的暴露点。

## 执行流程

```text
1. 读取阶段 3A/3B 产物，确认 tasks.md 已定稿
2. 协调者编写契约层（schema + 实体 + DTO/VO + 枚举 + 接口 + 公共层 + 构建配置）
3. 编译验证契约层
4. 按「模块」切分子代理，逐个下发任务书（白名单 + 验收标准 + 禁止项）
5. 协调者同时编写端到端冒烟脚本（在代理工作期间并行推进，不要空等）
6. 子代理完成后：全量编译 → 修复集成缺陷 → 运行冒烟脚本
7. 前端/部署等其余并行批次按同样方式推进
8. 最终整体构建 + 端到端验证 + 收尾（忽略规则、文档、任务状态回填）
```

### 并行度控制

- 并发代理数量有上限（本环境为 6）。超出时排队，先启动「关键路径」上的模块；
- 第一波优先启动「不依赖他人产出」的批次：基础设施、前端骨架、部署文档；
- 契约层由协调者完成后，再启动依赖契约的业务模块批次。

## 集成阶段常见缺陷（真实踩坑清单）

这些缺陷在单个模块内都编译通过，只有集成或真实运行时才暴露：

| 缺陷 | 现象 | 根因 | 预防 |
|---|---|---|---|
| 映射器扫描范围过宽 | 启动报 `Invalid bound statement`，Service 被当成 Mapper 注册 | 用包级扫描（如 `@MapperScan("根包")`）把 Service 接口也扫进去 | 只在 Mapper 接口上标注 `@Mapper`，不要用宽泛的包扫描 |
| 属性 getter 歧义 | MyBatis 报 `ambiguous type for property` | 同一布尔属性同时存在 `getXxx()` 与 `isXxx()` | 布尔属性只保留一套 JavaBean getter/setter |
| SQL 初始化脚本编码 | 中文种子数据乱码 | 初始化脚本按平台字符集读取（Windows 上为 GBK） | 显式声明脚本编码为 UTF-8 |
| 构建产物损坏 | 启动报 `ArrayIndexOutOfBoundsException` 读 jar | 多个代理并发执行 `clean package` 互相清理 target | 串行化打包，或为并行验证约定独立构建目录 |
| 前端用了未定义的样式类 | 功能正常但样式缺失 | 跨文件约定未落在共享样式里 | 集成时对照「组件用到的类名」与「样式表已定义的类名」 |
| 路由/入口未接线 | 页面跳转空白 | 路由表属共享文件，代理无权修改 | 共享文件的补齐列为协调者的收尾动作 |

**结论：交叉验证必须真实运行。**编译通过、单模块自测通过都不能替代「启动进程 + 真实请求 + 断言响应」。

## 端到端验证的要求

协调者应编写可重复执行的验证脚本，覆盖：

- **鉴权边界**：未登录、会话失效、账号被停用、越权访问；
- **参数校验**：每个字段的必填与长度上限，并断言**字段级错误载荷**（便于前端定位表单）；
- **状态派生逻辑**：由业务规则实时计算的状态（如临期/超期）要覆盖每个分支与边界当天；
- **错误码与 HTTP 状态**的对应关系；
- **写操作的结果一致性**：创建/编辑/删除后再查询，确认结果与失败时的行为；
- **重复启动幂等性**：初始化数据不重复插入、不报错。

脚本必须能**独立启动被测进程、跑完断言、清理退出**，并且断言失败时打印服务端日志尾部，便于定位。

## 环境与工具注意事项

- **依赖下载需要联网**：构建工具（Maven / npm）通常需要提权或走内网镜像；
- **前端构建**可能因调用系统子进程在沙箱内失败，需要提权重试；
- **文本编码**：源文件统一 UTF-8 且**不带 BOM**，否则编译器可能报错；写入时显式指定无 BOM 编码；
- **补丁工具**：某些环境的 `apply_patch` 对多行参数处理异常；此时改用「按行写入」的方式落文件，并在 skill 使用者说明里提示；
- **并行构建冲突**：多个代理同时执行会清理同一 `target`/`dist` 目录，约定串行打包或独立目录。

## 子代理完成后的核验

对每个子代理的产出，按顺序核验：

1. **范围合规**：确认只动了白名单内的文件（用版本控制状态或文件时间核对）；
2. **契约合规**：确认接口签名、字段名、错误码与冻结契约一致；
3. **验收对齐**：逐条对照 `TASK-###` 的验收标准，而不是听代理自己的结论；
4. **诚实度**：要求代理明确区分「已验证」与「未验证」，并保留未验证项由协调者补齐。

## 需要警惕的代理行为

- 自行「顺手」重构冻结契约或其他模块的文件 → 用白名单 + 禁止修改清单堵住；
- 只做编译自检就宣称完成 → 要求给出验收标准逐条对照，并由协调者实跑验证；
- 为了让构建通过而临时创建占位文件后忘记删除 → 收尾时全量核对并清理临时产物；
- 报告中使用「应该」「大概」等不确定措辞 → 要求提供可复现的命令与输出。
